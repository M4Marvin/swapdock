# Backup and restore

swapdock keeps its state in files, which is the point: you can back it up and
recover it without the tool. The automation is **partial**. `swapdock backup`
runs the app's dump command and `swapdock restore` runs its configured restore
command; scheduling, retention, restore verification and offsite copies are
still planned (G2.14/DATA-01). `swapdock export`/`import` is planned
(G1.5/DATA-02).

## What exists

| State | Path | Notes |
|---|---|---|
| Registry | `/srv/swapdock/apps/*.toml` | One file per app; the source of truth. Owned by the deploy user. |
| Compose overrides | `/srv/swapdock/overrides/*.yml` | Written by `adopt`; referenced by `compose_override`. |
| Deploy state | `/srv/swapdock/green/` | Root-owned; per-deploy generated overrides and the `pending/` crash-journal records. Include it for a faithful restore. |
| Run log | `/var/log/swapdock/swapdock.jsonl` | Append-only audit trail; rotated weekly. |
| Generated nginx | `/etc/nginx/conf.d/front-door.conf` | Regenerated by `apply`; restore or regenerate, do not hand-edit. |
| Hand-written nginx | `/etc/nginx/conf.d/00-swapdock-http.conf`, `/etc/nginx/snippets/proxy-common.conf`, `/etc/nginx/snippets/spa-fallback.conf` | Installed from `install/nginx/`. |
| App data | Docker volumes / host bind mounts | **Outside swapdock.** Back up each app with its native tool. |

## Back up the registry and state

Stop the API (if it is running) or at least avoid a deploy while you snapshot:

```bash
stamp="$(date +%F-%H%M)"
sudo tar -czf "/root/swapdock-state-$stamp.tgz" \
  -C / srv/swapdock/apps srv/swapdock/overrides srv/swapdock/green
sudo chmod 0600 "/root/swapdock-state-$stamp.tgz"

# Optional but useful: the audit trail and the hand-written nginx files.
sudo tar -czf "/root/swapdock-support-$stamp.tgz" \
  -C / var/log/swapdock etc/nginx/conf.d/00-swapdock-http.conf \
  etc/nginx/snippets/proxy-common.conf etc/nginx/snippets/spa-fallback.conf
```

Check the archive before you rely on it:

```bash
sudo tar -tzf "/root/swapdock-state-$stamp.tgz" | head -20
```

Paths contain no personal data by default, but a registry file can contain a
backup command with arguments. Treat the archive as sensitive and keep it
`0600`.

## App data

Each app can define a `[backup]` command:

```toml
[backup]
command = ["sqlite3", "/srv/example/shop/data/shop.db", ".backup {file}"]
restore_command = ["sqlite3", "/srv/example/shop/data/shop.db", ".restore {file}"]
verify_command = ["sqlite3", "{file}", "PRAGMA integrity_check;"]
offsite_command = ["rclone", "copy", "{file}", "remote:swapdock/shop/"]
dir = "/srv/swapdock/backups/shop"
before_deploy = true
keep = 14
```

`swapdock backup <app>` runs the dump **once**, on demand. `swapdock restore
<app> --file /srv/swapdock/backups/shop/<snapshot>` runs the restore command;
the file must exist, and a restore is a live-data mutation, so stop the app or
put it in maintenance first. The command is argv (no shell); placeholders are
`{file}`, `{app}`, `{release}` and `{timestamp}`, and the program must be on the
backup allowlist (the same policy as the dump command).

`verify_command` is optional: it runs after a successful dump with the same
placeholders and program allowlist, and a non-zero exit fails the backup.
`offsite_command` runs after verification with the same rules; it is how you copy
to S3/B2/rclone/rsync. `keep = N` prunes all but the newest N `<app>-*` files in
`dir`; unknown files are never deleted. `swapdock backup --all` applies all
three. The repository includes a real SQLite backup→verify→offsite→destroy→
restore test (`tests/backup_restore.rs`); it is not a disposable-host drill.
Today swapdock does not schedule runs itself, verify every app-specific restore,
or provide a hosted offsite destination. For anything that writes state:

- run the backup on a timer yourself (systemd timer/cron) until DATA-01 lands;
- copy the result off the host;
- restore it on a disposable host and prove it works before you need it.

## Schedule backups

`swapdock backup --all` runs every app's configured dump command. It is what the
optional systemd timer runs:

```bash
# installed with: sudo bash swapdock-dist/install-swapdock.sh --with-backup-timer swapdock-dist
sudo systemctl enable --now swapdock-backup.timer
systemctl list-timers swapdock-backup.timer
journalctl -u swapdock-backup.service -n 50
```

The timer runs daily at 03:30 with a randomized delay, does not catch up more
than once after downtime (`Persistent=true`), and does **not** enforce retention
or copy offsite. A failed app is reported on stderr and in the run log; a
`SWAPDOCK_WEBHOOK_URL` in `/etc/swapdock/api.env` also gets a failure webhook.
Run a restore drill before relying on it.

## Restore on the same host

1. **Stop the API and do not deploy while restoring.**

   ```bash
   sudo systemctl stop swapdock 2>/dev/null || true
   ```

2. **Restore the archive.**

   ```bash
   sudo tar -xzf /root/swapdock-state-<stamp>.tgz -C /
   ```

   If the archive was made with `-C /`, it contains `srv/swapdock/...` paths.
   Inspect it first; never extract an archive you have not listed.

3. **Restore ownership.** The registry belongs to the deploy user; the green
   directory is root-owned.

   ```bash
   sudo chown -R <deploy-user>:<deploy-user> /srv/swapdock/apps /srv/swapdock/overrides
   sudo chown -R root:root /srv/swapdock/green
   ```

4. **Check the registry and the host.**

   ```bash
   swapdock validate
   swapdock doctor
   swapdock render | diff -u /etc/nginx/conf.d/front-door.conf -
   ```

   `doctor` needs the compose files, images and healthchecks the registry
   refers to. On a fresh host those must exist before it can pass.

5. **Apply only when you are ready to change nginx.** `apply` is host-mutating,
   and Gate 2 (deploy/apply correctness) is still red in
   [LAUNCH.md](../LAUNCH.md). Do not apply while another deploy is running.
   Review the diff first and read [security.md](security.md).

## Restore on a new host

The registry is portable; the host is not. On a new supported host:

1. Follow [install.md](install.md) to install the same binary version and the
   nginx files.
2. Restore `srv/swapdock/apps` and `srv/swapdock/overrides` (and `green` if you
   need the exact recorded release chain).
3. Recreate or restore the app data and the compose files at the paths the
   registry names. The registry stores absolute `compose_dir`/`repo` paths, so
   a different layout requires editing the TOML.
4. Run `swapdock validate` and `swapdock doctor`.
5. Run `swapdock render` and compare it with what you expect before `apply`.
6. Do the first deploy on a disposable host if you can.

There is no `swapdock export`/`import` command yet; a tar of the registry is
the supported manual path.

## What is not backed up by this page

- Docker images and containers (rebuild or pull them).
- Docker volumes and bind-mounted app data (use each app's backup command).
- Cloudflare/tunnel configuration (swapdock never edits it).
- The systemd unit, sudoers and logrotate files (reinstall them).
- The console bundle (not distributable yet).
